Esta es una pregunta que solía contestar mal. Cuando escribo esto:

TSX
const view = <Greeting name="Ada" />;

¿cuándo se ejecuta Greeting? Durante mucho tiempo mi modelo mental fue "ahí mismo". Parece una llamada, al fin y al cabo. Pues no lo es. Esa línea nunca llama a Greeting, y entender qué hace en su lugar es la base de todo lo demás que hace React: volver a renderizar, saltarse trabajo, pausar un render a medias.

Así que en esta lección escribo la función en la que se compila JSX, le digo al compilador que la use e imprimo lo que sale.

El objetivo: un objeto plano

Antes de que nada llegue a la pantalla, React necesita saber qué quiero que haya ahí. Qué etiqueta o componente, con qué props, envolviendo a qué hijos. Se lo paso como un objeto plano, uno por etiqueta. React lo lee, lo compara con el del render anterior y lo tira. No hay nada más barato de construir y de tirar que un objeto plano, y con cuatro campos basta.

src/mini-react/shared.tsTypeScript
export const REACT_ELEMENT_TYPE = Symbol.for('mini-react.element');
export const REACT_FRAGMENT_TYPE = Symbol.for('mini-react.fragment');

export type Key = string | null;

export interface ReactElement<P = any> {
  $$typeof: symbol;
  type: any;
  key: Key;
  props: P;
}

export type ReactNode = ReactElement | string | number | boolean | null | undefined | ReactNode[];

type es lo que hay que dibujar: una cadena como 'li' para una etiqueta del DOM, o una función para un componente. key es una cadena o null. props es todo lo demás.

$$typeof es una marca que dice "este objeto es un elemento". Es un símbolo y no una cadena por una razón: un símbolo no se puede escribir en JSON. Si mi aplicación renderiza datos que vienen de un servidor, nadie puede dejar ahí un JSON que se haga pasar por un elemento, porque la marca no sobrevive al viaje.

La función a la que llama el compilador

No me toca elegir ni el nombre ni los argumentos de esta función. Los elige el compilador. Con la transformación "automática" de JSX, cada etiqueta se convierte en una llamada a jsx, importada de <import source>/jsx-runtime. En un servidor de desarrollo es jsxDEV, de <import source>/jsx-dev-runtime. Los argumentos son siempre los mismos tres y en el mismo orden: el tipo, un objeto con las props y la key. Mi trabajo es poner en esa dirección una función que haga lo correcto con ellos.

src/mini-react/jsx-runtime.tsTypeScript
import { REACT_ELEMENT_TYPE, REACT_FRAGMENT_TYPE, type ReactElement, type Key } from './shared';

export const Fragment = REACT_FRAGMENT_TYPE;

export function jsx(type: any, config: any, maybeKey?: any): ReactElement {
  let key: Key = null;
  if (maybeKey !== undefined) key = '' + maybeKey;
  if (config != null && config.key !== undefined) key = '' + config.key;

  const props: Record<string, any> = {};
  for (const name in config) {
    if (name !== 'key') props[name] = config[name];
  }

  // Elements (and their props) are immutable. Freezing them makes accidental
  // mutation throw, exactly like React does in development.
  Object.freeze(props);
  return Object.freeze({ $$typeof: REACT_ELEMENT_TYPE, type, key, props });
}

// The compiler calls `jsxs` when it built the children array itself
// (two or more children written in the source). Same object either way.
export const jsxs = jsx;

/** The dev transform passes extra debug args; we ignore them. */
export function jsxDEV(type: any, config: any, maybeKey?: any): ReactElement {
  return jsx(type, config, maybeKey);
}

Un par de cosas que merece la pena señalar:

  • La key se convierte en cadena. '' + maybeKey hace que key={7} y key="7" sean la misma key. La segunda comprobación cubre una key que llega dentro del objeto de props, que es lo que pasa cuando haces spread de un objeto que contiene una.
  • La key queda fuera de props. Por eso props.key es undefined dentro de un componente. La key es para React, para distinguir a los hermanos entre sí.
  • Nada más es especial. children se copia como cualquier otra prop. Lo mismo pasa con ref, que es una prop normal desde React 19.
  • Los dos objetos están congelados. Un elemento describe un momento. Si se pudiera cambiar después, compararlo con la siguiente descripción no tendría ningún sentido.
  • Fragment es el símbolo. Para <>…</>, el compilador importa Fragment de este archivo y lo pasa como tipo. No es un componente.

jsxs y jsxDEV son nombres que el compilador usa en situaciones concretas. jsxs es para etiquetas con varios hijos escritos a mano. jsxDEV es lo que llama un servidor de desarrollo, con tres argumentos extra (un flag, la ubicación en el código fuente, this) que el React real usa para las advertencias. Aquí todas construyen el mismo objeto.

Decirle al compilador dónde está

Algo que no noté durante años: todo archivo con JSX recibe un import que nadie escribió. Lo añade el compilador.

TSX
const view = <Greeting name="Ada" />;
JavaScript
import { jsx as _jsx } from 'mini-react/jsx-runtime';
const view = _jsx(Greeting, { name: 'Ada' });

se compila a

De ese import solo elijo una palabra, mini-react. Es el import source. El compilador le pega /jsx-runtime por su cuenta (/jsx-dev-runtime en un servidor de desarrollo). Así que hacer que esto funcione se reduce a tres cosas. TypeScript tiene que conocer el nombre, Vite también, y cada ruta que importa el código compilado tiene que llevar a un archivo real.

TypeScript: de dónde viene JSX

TypeScript es quien revisa mi JSX, en el editor y en yarn typecheck, así que tiene que estar de acuerdo en el import source. También necesita paths, porque mini-react no está instalado en ningún sitio: es una carpeta de mi proyecto. Ambas cosas van en tsconfig.json:

JSON
"jsx": "react-jsx",
"jsxImportSource": "mini-react",
"paths": {
  "mini-react": ["./src/mini-react/index.ts"],
  "mini-react/*": ["./src/mini-react/*"]
}

Vite: compilar y encontrar los archivos

Pero TypeScript solo comprueba. El código que ejecuta el navegador lo compila Vite (con oxc), así que Vite recibe el mismo import source. Además necesita un alias, por la misma razón que TypeScript necesitaba paths: cuando el código compilado importa mini-react/…, Vite tiene que cargarlo de mi carpeta. En vite.config.ts:

TypeScript
resolve: {
  alias: [
    { find: /^mini-react$/, replacement: `${lib}/index.ts` },
    { find: /^mini-react\/(.*)$/, replacement: `${lib}/$1` },
  ],
},
oxc: { jsx: { runtime: 'automatic', importSource: 'mini-react' } },

Los archivos que importa el código compilado

Un build de producción importa mini-react/jsx-runtime, que es el archivo que acabo de escribir. El servidor de desarrollo pide mini-react/jsx-dev-runtime, así que ese archivo también tiene que existir. No tiene nada dentro: solo reexporta lo mismo:

src/mini-react/jsx-dev-runtime.tsTypeScript
export { jsxDEV, Fragment, jsx, jsxs } from './jsx-runtime';
export type { JSX } from './jsx-runtime';

mini-react a secas, sin nada detrás, es el punto de entrada del paquete. Ahí es donde la demo importa sus tipos:

src/mini-react/index.tsTypeScript
import { REACT_FRAGMENT_TYPE } from './shared';

export { jsx, jsxs, createElement } from './jsx-runtime';
export type { ReactNode, ReactElement } from './shared';

// `as any` so TypeScript accepts <Fragment> as a JSX tag (it is a symbol, not a function).
export const Fragment = REACT_FRAGMENT_TYPE as any;

TypeScript: qué etiquetas existen

Aunque el compilador ya esté resuelto, TypeScript sigue teniendo opiniones sobre cada etiqueta que escribo. Quiere saber si li es una etiqueta, qué props acepta y qué tipo acaba teniendo <li>A</li>. No lo adivina: busca un namespace llamado JSX exportado por el módulo del runtime y lee ahí las respuestas.

Los tipos del React real enumeran cada etiqueta HTML, cada una con sus props. No voy a escribir todo eso para un curso, así que mini-react toma el camino perezoso. La firma de índice de IntrinsicElements deja pasar cualquier etiqueta con cualquier prop. El resto es pequeño. Element dice que el tipo de una etiqueta es un ReactElement, ElementChildrenAttribute dice que los hijos llegan en la prop children, e IntrinsicAttributes deja que cualquier etiqueta lleve una key. Esto continúa jsx-runtime.ts:

src/mini-react/jsx-runtime.tsTypeScript
export namespace JSX {
  export type Element = ReactElement;
  export interface ElementChildrenAttribute {
    children: {};
  }
  export interface IntrinsicAttributes {
    key?: string | number | null;
  }
  export interface IntrinsicElements {
    [elementName: string]: any;
  }
}

createElement: elementos sin compilador

Antes de que existiera la transformación automática, JSX se compilaba a createElement(type, props, ...children). También es lo que llamarías a mano si no hubiera compilador, así que quiero tenerlo a mano. Eso sí, sus argumentos tienen otra forma: la key viaja dentro de las props y los hijos llegan como argumentos extra. Por eso en mini-react es un pequeño adaptador delante de jsx: mueve los hijos a props.children y le pasa lo demás. Otra vez en el mismo archivo:

src/mini-react/jsx-runtime.tsTypeScript
/** Classic API: createElement(type, props, ...children). */
export function createElement(type: any, config: any, ...children: any[]): ReactElement {
  const props: Record<string, any> = { ...(config ?? {}) };
  if (children.length === 1) props.children = children[0];
  else if (children.length > 1) props.children = children;
  return jsx(type, props);
}

Echarle un vistazo

Toca ver qué produce todo esto. Aquí abajo, cada trozo del JSX de la demo está junto al objeto que jsx devuelve para él, tal cual lo imprime la demo. La única trampa es que JSON no puede contener símbolos ni funciones, así que la demo los escribe como texto.

TSX

La A entre las etiquetas se convirtió en children: "A". Los hijos son, de verdad, una prop con una sintaxis más cómoda. La key entró como tercer argumento de la llamada, así que nunca se acerca a props.

Esta vez type es la propia función Greeting, y props contiene name. No hay children porque no escribí nada entre las etiquetas. Y tampoco hay h1. Greeting devolvería uno, pero todavía nadie la ha llamado.

Resulta que el Fragment también es un elemento normal, con el segundo símbolo de shared.ts como tipo. Sus hijos son los dos objetos de arriba, lo que convierte toda la demo en un único objeto anidado.

La demo que imprime todo esto no renderiza nada. Escribe JSX e imprime en qué se convirtió. Tiene un truco: al convertir una función en cadena obtienes su código fuente, y el código fuente que tiene el navegador es el compilado. Así que una función flecha con JSX dentro me puede enseñar exactamente lo que escribió el compilador.

El código completo de la demo
src/demo.tsxTSX
/**
 * DEMO — JSX is data
 * ==================
 *
 * Nothing here renders anything. We write JSX, then print what it turned into.
 */
import type { ReactElement } from 'mini-react';

const root = document.getElementById('root')!;

// JSON.stringify drops symbols and functions, so turn them into text first.
function show(element: ReactElement): string {
  const readable = (_key: string, v: unknown) =>
    typeof v === 'symbol' ? String(v) : typeof v === 'function' ? `function ${v.name}` : v;
  return JSON.stringify(element, readable, 2).replace(/"(Symbol\(.+?\)|function \w+)"/g, '$1');
}

function print(title: string, text: string): void {
  const h2 = document.createElement('h2');
  h2.textContent = title;
  const pre = document.createElement('pre');
  pre.textContent = text;
  root.append(h2, pre);
}

// 1. One element. A function's source is whatever the compiler emitted for it.
const item = () => <li key="a">A</li>;
print('What the compiler wrote', String(item));
print('What that call returns', show(item()));

// 2. A tree: a component, a keyed list, and a Fragment around both.
let calls = 0;
function Greeting(props: { name: string }) {
  calls++;
  return <h1>Hello, {props.name}</h1>;
}

const tree = (
  <>
    <Greeting name="Ada" />
    <ul className="menu">
      {['a', 'b'].map((id) => (
        <li key={id}>{id.toUpperCase()}</li>
      ))}
    </ul>
  </>
);
print('The tree', show(tree));
print('Times Greeting was called', String(calls));

Nota

No quites la línea import type. Un archivo .tsx sin ningún import ni export se compila como script, y la página falla al llegar a require.

La página empieza con el li suelto. Primero, la llamada que escribió el compilador para él; después, lo que devuelve esa llamada.

Times Greeting was called

0

Donde está Greeting no hay ningún h1 ni ningún "Hello, Ada". Hay type: function Greeting y sus props, y el contador marca 0. JSX guardó la función y nunca la llamó. Quien lea este árbol más adelante decidirá cuándo llamarla, si la llama siquiera, y cuántas veces. Fíjate también en lo que más falta: no hay nodos del DOM, ni punteros al padre, ni estado.

A eso me refiero con el árbol de elementos. Es lo que produjo JSX, y nada más. Tampoco es el árbol de fibers, y es fácil confundirlos. El árbol de fibers es la estructura que React conserva entre renders, y la construyo a mano en la siguiente lección, Árbol de fibers. Los dos se encuentran en First paint. Ahí, beginWork convierte estos elementos en fibers a medida que el recorrido llega a ellos, y renderizar el fiber de Greeting es el momento en que por fin se llama a Greeting y se crea su h1.

Lo que he dejado fuera

  • No hay advertencias. El React real comprueba si faltan keys en los arrays y si llegan keys a través de un spread. Esa es la única razón por la que jsxs y jsxDEV están separadas de jsx; aquí son alias.
  • Las etiquetas no tienen tipos de verdad. Cualquier nombre de etiqueta con cualquier prop pasa la comprobación de tipos.
  • No están los campos de depuración que el React real añade a los elementos en desarrollo (owner, stack).
  • No se renderiza nada. La página se construye con llamadas directas al DOM porque todavía no existe nada capaz de dibujar un elemento.

Hacia dónde va esto

Un elemento es una petición. Se reconstruye y se desecha constantemente, así que no puede ser el lugar donde React recuerda nada. Las dos próximas lecciones, Árbol de fibers y Host del DOM, construyen el objeto que React conserva entre un render y otro, y la pequeña API que usa para hablar con el DOM. Cuando esas tres piezas se unan en el hito First paint, por fin habrá algo que recorra un árbol como el de arriba, llame a Greeting y ponga un h1 en la pantalla.
